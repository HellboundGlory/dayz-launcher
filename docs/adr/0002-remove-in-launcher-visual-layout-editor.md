# Remove the in-launcher visual layout editor; inspector-only going forward

Phase 3.5 had already shipped and merged a working drag-to-reorder/hide/resize visual editor for Advanced-tier `layout.json`, built directly into Dev Mode. With Expert-tier composition now covering ~11 slots with a much richer vocabulary (free positioning, decorative images) and committed to text-file authoring only (a visual editor for that is deliberately deferred, its own future phase, not co-built with the format), keeping a visual editor for just the Advanced-tier subset created an inconsistent authoring model — draggable for simple cases, text-only for everything else — for a persona (an author reaching for Expert tier) already comfortable in a text file. It was also a maintenance-heavy surface in this codebase specifically: the drag mechanism needed a WebKitGTK-specific workaround (plain document-level mouse events, not Pointer Events capture) and had already produced a real chain of usability bugs caught only through live interactive testing.

We removed `LayoutEditPopover.tsx`, the drag-reorder/hide interactions, the sidebar resize handle, and the store actions that existed only to serve them, keeping the Dev Mode inspector badge (slot id, required/optional children, copy-selector) as the sole in-launcher authoring aid. All layout capabilities remain fully available via hand-edited `layout.json`/`components/*.json` plus existing live hot-reload — nothing is lost, only the drag UI on top of it. The backend activation-arm/confirm/revert and file-watch hot-reload plumbing is unaffected; it serves saved-file edits regardless of whether a human or a UI wrote them.

This reverses §9.1 of the original theme-system proposal, which explicitly argued against a *separate bundled app* on the grounds that it would be a second rendering surface to keep in sync with every future core UI change. That concern was about a separate app, not an in-launcher visual editor, so it doesn't directly contradict this decision — but it's adjacent enough to flag: a possible future standalone theme-editing app (raised as a "maybe, later" in this same conversation, not committed) would need to consciously re-weigh the drift/accuracy risk §9.1 named, not silently ignore it.
